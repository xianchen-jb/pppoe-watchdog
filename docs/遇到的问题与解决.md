# 遇到的问题与解决过程

> 这份文档按「发现顺序」记录做这个项目时踩到的 17 个坑。每个坑尽量写清：**当时看到什么现象 → 怎么查 → 真正的原因 → 怎么解决**。

> 对后来者：脚本本身只有三百多行，真正花时间的是下面这些排查。尤其是第 1 条和第 12 条 —— 不知道这两点，方向会整个跑偏。

## 一、先把「睡眠」这件事搞清楚

### 1. 这台机器根本没有传统睡眠，只有 Modern Standby

**现象**

我的原始需求是「电脑一休眠宽带就掉，能不能让它别掉」。直觉上这是个网卡设置问题：进设备管理器勾一下「允许此设备唤醒计算机」，问题应该就解决了。

**排查**

```
> powercfg /a
此系统上有以下睡眠状态:
    待机 (S0 低电量待机) 连接的网络
    休眠
    快速启动

此系统上没有以下睡眠状态:
    待机 (S1)  ── 系统固件不支持此待机状态
    待机 (S2)  ── 系统固件不支持此待机状态
    待机 (S3)  ── 系统固件不支持此待机状态
```

S1/S2/S3 **全部**是「系统固件不支持」。

**原因**

这台笔记本实现的是 **Modern Standby（现代待机，S0 低电量待机）**。它跟传统睡眠的本质区别是：睡眠期间 CPU 和网络协议栈**仍在低功耗运行**，而不是像 S3 那样整体断电。

这解释了一件反直觉的事：**我原来以为的「休眠」其实是 S0 待机**。而在 S0 待机下，PPPoE 会话并不能靠「网卡唤醒包」救回来 —— 会话本身已经断了。

**解决**

放弃了「配网卡唤醒、让它睡着也别掉」这条路线，改成 **常驻进程轮询 + 发现断了就重拨**。这样不管掉线原因是睡眠、网线松动还是运营商踢人，走的都是同一条恢复路径。

**顺带确认**：`PCSystemType=2`（Mobile）且有电池，确实是笔记本，没有「插网线当台式机用」的选项。

---

### 2. 千万不要为了「变回 S3」去禁用 Modern Standby

**当时想过的一个方案**

网上有教程说可以改注册表 `PlatformAoAcOverride = 0` 让系统退回传统 S3 睡眠 —— 因为 S3 下「网卡唤醒 + 会话保持」理论上更靠谱。

**为什么没做**

查清楚之后发现这条路是**更差**的：Modern Standby 一旦被禁用，这台机器就是「没有睡眠」的状态 —— 要么完全不睡，要么只能走休眠（把内存写到硬盘、整机关机）。开机恢复时间从几秒变成几十秒，比现在「醒了重拨一次」糟糕得多。

**结论**

**没动这个注册表。** 与其把系统掰回一个它不支持的形态，不如接受 Modern Standby，把「醒来后多快连回来」这个可优化项做到极致。

---

### 3. 拨号必须在用户会话里做，SYSTEM 身份的服务拨不了

**现象**

最初想把守护做成 Windows 服务（开机就起、不依赖登录）。写完之后 `rasdial` 一直失败。

**原因**

PPPoE 拨号连接由 **RasMan（远程访问连接管理器）**在**用户会话**内维护。SYSTEM 身份的服务运行在 session 0，那里没有用户的拨号连接上下文，所以 `rasdial 宽带连接` 找不到目标连接。

**解决**

计划任务用「**登录时触发** + 以最高权限运行 + 交互式用户身份」：

```powershell
$trigger = New-ScheduledTaskTrigger -AtLogOn
$trigger.Delay = 'PT5S'
$principal = New-ScheduledTaskPrincipal -UserId $env:USERNAME -LogonType InteractiveToken -RunLevel Highest
```

代价是**必须先登录 Windows 才能拨号**。为了减少这一步的摩擦，另外配置了自动登录（见 `docs/使用手册.md`），让「开机 → 自动登录 → 5 秒后自动拨号」串成一条。

## 二、网卡与驱动

### 4. `Get-NetAdapterPowerManagement` 直接报「系统错误 31」

**现象**

想用 PowerShell 关掉网卡的省电选项，标准做法是：

```powershell
Get-NetAdapterPowerManagement -Name '以太网' | Set-NetAdapterPowerManagement -WakeOnMagicPacket $true
```

结果报错：

```
Get-NetAdapterPowerManagement : 连到系统上的设备没有发挥作用。
（Windows System Error 31）
```

**排查**

一开始怀疑是网卡名写错了。`Get-NetAdapter` 输出里确实有好几个名字很像的设备（`WLAN`、`WLAN 2`、`WLAN 4`……其中一些状态是 `Not Present`），以为选中了幽灵设备。换成确定的 `以太网` 之后**同样报错**。

**原因**

这个 cmdlet 背后查的是 WMI 类 `MSFT_NetAdapterPowerManagementSettingData`。**这块 Realtek 2.5GbE 网卡的驱动没有实现这个类**，所以查询直接失败 —— 跟名字无关，是这个驱动压根不提供。

**解决**

绕开 WMI，改用**高级属性**接口：

```powershell
Get-NetAdapterAdvancedProperty -Name '以太网' |
    Select-Object DisplayName, DisplayValue, RegistryKeyword
```

这个接口读的是驱动自己注册的注册表键，覆盖面广得多。实测能读到 `环保节能`、`Gigabit Lite`、`Power Saving Mode`、`魔术封包唤醒`、`网络唤醒和关机连接速度` 等十几项。

**教训**：遇到「系统错误 31」这类驱动层报错，先怀疑**驱动没实现某个接口**，而不是参数写错了。

---

### 5. 幽灵网卡把批量操作搞崩

**现象**

```powershell
Get-NetAdapter | ForEach-Object { ... }   # 报错，或操作到了不存在的设备
```

**原因**

`Get-NetAdapter` 默认不列隐藏设备，但 `(Get-NetAdapter).Name` 在某些情况下会返回包含 `Not Present` 状态的条目（这台机器上有一堆 `WLAN 2/3/4/5`、`以太网(内核调试器)`）。

**解决**

所有网卡操作都**精确指定名字**，不用 `ForEach-Object` 遍历。需要看全量时用 `-IncludeHidden` 并显式过滤状态：

```powershell
Get-NetAdapter -IncludeHidden | Where-Object Status -ne 'Not Present'
```

真正该操作的那张卡：

```
Name           InterfaceDescription                          Status
----           --------------------                          ------
以太网          Realtek 2.5GbE Family Controller         Up
```

### 6. 2.5GbE 的网卡，链路只跑到 100 Mbps

**现象**

`Get-NetAdapter` 里 `LinkSpeed` 显示 `100 Mbps`，但这张卡是 2.5 吉比特的。

**排查**

把高级属性全拉出来对比，发现三个省电项**全是开启**：

| DisplayName | 值 | 影响 |
| --- | --- | --- |
| `环保节能`（Green Ethernet） | 开启 | 空闲时降功率，可能降速 |
| `Gigabit Lite` | 开启 | 用信号质量换功耗 |
| `Power Saving Mode` | 开启 | 进一步省电 |

再叠加 `网络唤醒和关机连接速度 = 10 Mbps 优先`。

**解决**

`tune-nic.ps1` 把上面三项关掉、唤醒速度改成「不降速优先」，并关掉快速启动（见第 7 条）。脚本**默认只预览**，加 `-Apply` 才真写：

```powershell
.\scripts\tune-nic.ps1           # 列出会改什么、当前值是什么
.\scripts\tune-nic-apply.bat     # 真正写入（需管理员，链路会重新协商几秒）
```

**注意**：改完**必须拔插一次网线**（或重启）才会按新速率重新协商。另外如果墙上网口 / 交换机本身只有百兆，那降速跟网卡设置无关 —— 这一点要先用别的机器验证，别白折腾。

### 7. 快速启动让网卡状态「带病」跨重启

**现象**

每次开机后，以太网链路要好几秒才 `Up`，守护脚本得等着。

**原因**

```
HiberbootEnabled = 1
```

**快速启动（Fast Startup）**本质是「关机时把内核会话休眠到硬盘、开机时读回来」，而不是真正重新初始化硬件。结果就是网卡驱动带着上一次运行的状态醒来，链路重新协商的时间被拉长，偶发的小毛病也会被继承。

**解决**

`tune-nic.ps1` 里一并关掉：

```powershell
Set-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Power' `
                 -Name HiberbootEnabled -Value 0
```

代价是开机慢一两秒，换来的是每次都是干净状态。

## 三、PowerShell 与编码

### 8. 无 BOM 的 UTF-8 脚本被按 GBK 解析，中文全变乱码

**现象**

脚本写完，双击 bat 运行，报了一堆莫名其妙的语法错误：

```
Unexpected token '浠庣湡瀹炴枃浠舵埅鍙栦唬鐮佸潡锛氱' in expression or statement.
Missing closing '}' in statement block or type definition.
```

**原因**

脚本文件是 **UTF-8 无 BOM**，而 **Windows PowerShell 5.1 在没有 BOM 时按系统 ANSI 代码页（简体中文 = GBK/936）解析脚本**。于是一个中文字符被当成多个乱码字节，引号、括号的配对全乱了 —— 所以报的错跟真正的问题毫无关系。

**解决**

所有 `.ps1` 统一存成 **UTF-8 with BOM**。

补 BOM 的一次性操作：

```powershell
$p = 'C:\Tools\pppoe\pppoe-watchdog.ps1'
$t = [System.IO.File]::ReadAllText($p, (New-Object System.Text.UTF8Encoding($false)))
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
```

**这次踩了两遍**：第二次是有个临时测试脚本，用编辑器写出又是无 BOM，同样的乱码、同样的报错。**只要改完 .ps1，就顺手检查一次 BOM。**

检查方法：

```powershell
$b = [System.IO.File]::ReadAllBytes($p)
$hasBom = $b.Length -ge 3 -and $b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF
```

`bat` 文件不用动 —— 它们只调用 powershell.exe，本身是纯 ASCII。

### 9. 日志文件每次写入都追加一个 BOM

**现象**

日志里时不时冒出一行怪东西：`﻿2026-10-25 08:59:44 [INFO] ...`

**原因**

写日志的函数每次都这么写：

```powershell
Add-Content -Path $LogPath -Value $line -Encoding UTF8
```

`-Encoding UTF8` 在 PS 5.1 里是「UTF-8 **带 BOM**」，而且 `Add-Content` **每次调用都会重新写一遍 BOM 头**（它不知道文件已经存在）。于是每写一条日志就多一个 BOM 字节。

**解决**

改成手动控制 —— 只在文件不存在时写一次 BOM，后续追加用无 BOM 编码：

```powershell
function Write-Log {
    param([string]$Level, [string]$Message)
    $line = '{0} [{1}] {2}' -f (Get-Date -Format 'yyyy-MM-dd HH:mm:ss'), $Level, $Message
    $noBom = New-Object System.Text.UTF8Encoding($false)
    if (-not (Test-Path $script:LogPath)) {
        [System.IO.File]::WriteAllText($script:LogPath, $line + "`r`n", (New-Object System.Text.UTF8Encoding($true)))
    } else {
        [System.IO.File]::AppendAllText($script:LogPath, $line + "`r`n", $noBom)
    }
}
```

**顺带学到的**：PS 5.1 的 `-Encoding UTF8` 和 PS 7 的 `utf8` **不是一回事**（前者带 BOM、后者不带）。写跨版本脚本时这个差异很坑。

### 10. `$pid` 是只读自动变量，不能拿来当循环变量

**现象**

```powershell
foreach ($pid in $procs) { ... }   # 报错
```

**原因**

`$PID` 是 PowerShell 的**自动变量**，保存当前进程 ID，**只读**。大小写不敏感，所以 `$pid` 也会撞上。

**解决**

换个名字，比如 `$procId`。同类还有 `$host`、`$input`、`$args`、`$error`、`$?` —— 这些都不该当普通变量用。

### 11. `Read-Host -AsSecureString` 无法从管道喂密码

**现象**

想自动化测试配置流程，把密码用管道喂进去，结果拿不到值：

```powershell
'MyPassword' | powershell -File setup.ps1    # Read-Host 依然卡住/读空
```

**原因**

`Read-Host -AsSecureString` 走的是**控制台输入**，不读 stdin 重定向。

**解决**

配置函数加一个可选参数供测试注入，交互路径仍然用 `Read-Host`：

```powershell
param([SecureString]$Password)
if (-not $Password) { $Password = Read-Host '请输入宽带密码' -AsSecureString }
```

## 四、计划任务与进程管理

### 12. `MultipleInstances=IgnoreNew` 让改完的代码一直不生效

**这条最坑，因为它伪装成「代码没写对」。**

**现象**

改完脚本、重跑 `install.bat`、再跑 `-Check` —— **行为跟改之前一模一样**。日志里没有新逻辑的输出。

**排查**

看时间戳对不上：

```
脚本文件最后修改时间 : 17:15:56
守护进程启动时间     : 16:52:32   ← 早了 23 分钟
```

**原因**

计划任务注册时设置了**单实例**：

```powershell
$settings.MultipleInstances = 'IgnoreNew'
```

它的语义是「已有实例在跑，就**忽略新的启动请求**」。而原来的 `install.ps1` 只做了两件事：`Register-ScheduledTask -Force`（覆盖定义）+ `Start-ScheduledTask`（启动）。

**覆盖任务定义不会杀掉正在运行的进程**。旧进程还活着占着实例位，`Start-ScheduledTask` 一看「已经有了」就直接忽略 —— 于是**跑的一直是 23 分钟前的旧代码**，文件改了等于没改。

**解决**

`install.ps1` 里显式先停、等退出、再起：

```powershell
# 1) 先停掉正在跑的旧实例
if (Get-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue) {
    Stop-ScheduledTask -TaskName $TaskName -ErrorAction SilentlyContinue
    # 2) 等进程真正退出（最多 10 秒）
    $deadline = (Get-Date).AddSeconds(10)
    while ((Get-Date) -lt $deadline) {
        if (-not (Get-Process -Id $script:OldPid -ErrorAction SilentlyContinue)) { break }
        Start-Sleep -Milliseconds 300
    }
}

# 3) 覆盖定义并启动
Register-ScheduledTask -TaskName $TaskName -Action $action -Trigger $trigger -Settings $settings -Principal $principal -Force | Out-Null
Start-ScheduledTask -TaskName $TaskName

# 4) 打印新进程 PID，让"到底换没换"一眼可见
Start-Sleep -Seconds 2
$newPid = (Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
           Where-Object { $_.CommandLine -like '*pppoe-watchdog*' }).ProcessId
Write-Host "新守护进程 PID = $newPid"
```

**教训**：配置文件改了、任务重注册了，**不等于运行中的进程换了**。任何「改代码 → 重启服务」的流程，都要显式确认旧实例真的死了。

### 13. 提权进程的命令行查不到，差点以为守护没在跑

**现象**

```powershell
Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
    Where-Object CommandLine -match 'pppoe-watchdog'
# → 空结果
```

但 `Get-ScheduledTask PppoeWatchdog` 状态明明是 `Running`。两边矛盾。

**原因**

守护进程是**以最高权限（提权）运行的**，而我的查询 shell 是普通权限。**非提权进程读不到提权进程的 `CommandLine`**（返回 `$null`），所以过滤条件全部落空 —— 进程其实好好地跑着。

**解决**

判定「守护是否在运行」改用**双判据**，都不依赖读取提权进程的命令行：

1. **互斥体**：守护启动时持有 `Local\PppoeWatchdog`，这是普通权限**也能**尝试打开并检测到「已被占用」的内核对象。
2. **计划任务状态**：`(Get-ScheduledTask -TaskName PppoeWatchdog).State`。

```powershell
function Test-DaemonRunning {
    try {
        $m = [System.Threading.Mutex]::OpenExisting('Local\PppoeWatchdog')
        $m.Dispose()
        return $true
    } catch { return $false }
}
```

（`OpenExisting` 只在「已存在」时成功，不会像 `New-Object Mutex` 那样顺手创建一个出来。）

`-Check` 自检里因此多了独立的「守护进程」一行，不再靠猜。

### 14. 按关键字杀进程，把自己也杀了

**现象**

调试时想清掉所有守护进程：

```powershell
Get-Process | Where-Object { $_.ProcessName -like '*pppoe*' } | Stop-Process -Force
```

结果**当前这个 shell 也一起没了**，后面的命令全没执行。

**原因**

匹配条件太宽 —— 我自己的命令行里就带着 `pppoe` 字样（比如 `powershell -File ...pppoe-watchdog.ps1`），于是自杀。

**解决**

三重收紧：排除自己和父进程、按可执行文件名精确匹配、按参数精确匹配：

```powershell
$self = $PID
$parent = (Get-CimInstance Win32_Process -Filter "ProcessId=$PID").ParentProcessId

Get-CimInstance Win32_Process -Filter "Name='powershell.exe'" |
    Where-Object {
        $_.ProcessId -ne $self -and
        $_.ProcessId -ne $parent -and
        $_.CommandLine -like '*-File*pppoe-watchdog.ps1*' -and
        $_.CommandLine -notlike '*-Check*'
    } |
    ForEach-Object { Stop-Process -Id $_.ProcessId -Force -ErrorAction SilentlyContinue }
```

最后那个 `-notlike '*-Check*'` 是为了不误杀「只是来查状态」的短命进程。

## 五、性能优化

### 15. `Test-Connection` 在断网时要干等 8.5 秒

**这条是整个优化里性价比最高的一处。**

**现象**

掉线后要三十多秒才恢复，比预期慢很多。拆日志发现每次「探测」都特别慢。

**排查**（打桩实测，目标换成不可达地址）

```powershell
Measure-Command { Test-Connection -ComputerName 192.0.2.1 -Count 2 -Quiet }
# → 8.5 秒
```

**原因**

`Test-Connection` 默认 **每个目标 ping 4 次、每次超时 4 秒**。打到不通的地址时，「2 次探测 × 4 秒 + 间隔」就是 8.5 秒。守护逻辑里「连续 2 次不通才算掉线」，光确认就花了 17 秒，再加上其它等待，36 秒就是这么来的。

**解决**

换成 .NET 的 `Ping`，**显式压超时、多目标并联判断**：

```powershell
$ProbeList      = @('223.5.5.5', '119.29.29.29', '180.76.76.76')
$ProbeTimeoutMs = 600

function Test-Online {
    foreach ($target in $ProbeList) {
        $ping = New-Object System.Net.NetworkInformation.Ping
        try {
            $r = $ping.Send($target, $ProbeTimeoutMs)
            if ($r.Status -eq 'Success') { return $true }
        } catch { } finally { $ping.Dispose() }
    }
    return $false
}
```

关键点：
- **600ms 超时** —— 通的话 40ms 就返回，不通时最多等 0.6 秒。
- **多个目标，任一可达即算正常** —— 避免单个 DNS 服务器抽风被误判成断网。

实测结果：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 单次探测耗时（不通时） | 8.5 秒 | 0.5 ~ 1.2 秒 |
| 掉线确认总耗时 | 36 秒 | 4 秒 |

顺带把「确认不通」的二次复检间隔从 10 秒压到 **1 秒**（`$RecheckDelay`），进一步加速。

### 16. 健康判定把「网卡状态」和「公网可达」混在一起，刚唤醒时误报

**现象**

日志里出现过自相矛盾的一条：

```
17:00:24 [WARN] 疑似掉线  PPPoE=False  公网=True
```

网明明是通的（`公网=True`），却报了掉线警告。

**原因**

原来的健康判定要求**两个条件同时成立**：

```powershell
$healthy = $pppUp -and $online    # ← 有问题
```

而 `$pppUp` 查的是「PPPoE 网卡的状态」。刚唤醒时，网卡的配置状态有**秒钟级的滞后** —— 公网已经通了，但网卡状态还没刷新成 `Up`。于是被判成不健康，连续两次就会触发一次**完全没必要**的重拨（自己把自己的网掐一下）。

**解决**

健康判定**只看公网可达性**，网卡状态降级为日志诊断信息：

```powershell
$healthy = $online      # 唯一的判据
# $pppUp 只用于日志，帮助事后分析
```

道理很简单：**用户关心的是「能不能上网」，不是「网卡状态字段长什么样」**。公网可达就是唯一权威信号。

### 17. 开机到有网要 40 秒 —— 拆开看每一项

**现象**

冷启动后大约 40 秒才有网。虽然比手动拨号省事，但还是慢。

**拆解**（从日志各阶段时间戳反推）

| 阶段 | 耗时 | 能不能压 |
| --- | --- | --- |
| 开机 → Windows 登录界面 | ~4 秒 | 不能（硬件） |
| 登录 → 计划任务触发 | **20 秒** | 能，改 `Delay` |
| 探测确认（2 次 × 8.5s → 优化后 2 × 0.5s） | 5.5 秒 | 能，见第 15 条 |
| 查链路 / 等链路就绪 | 3 秒 | 不能（物理协商） |
| `rasdial` 协商 | **8 秒** | 不能（运营商侧） |

**优化 A：把登录延迟从 20 秒改成 5 秒**

```powershell
$trigger = New-ScheduledTaskTrigger -AtLogOn
$trigger.Delay = 'PT5S'     # 原来是 PT20S
```

原来留 20 秒是担心「桌面还没起来，网络栈没准备好」。实际上守护脚本自己有「等链路就绪（最多 60 秒）」的逻辑，这 20 秒纯属浪费。

**优化 B：加一条「快速通道」，开机时跳过探测**

刚开机时 PPPoE 会话**必然不存在**，没必要先探测两次、确认掉线、再重拨 —— 那是白等 5 秒。

```powershell
# 启动时先查一次会话
if (-not (Test-PppoeUp)) {
    # 会话确实不存在 → 等链路就绪后直接拨，跳过探测
    Wait-LinkReady
    Invoke-Dial
} else {
    # 会话存在（可能是睡眠唤醒的"假活"）→ 交给正常循环判断
}
```

**关键在于「只在会话确实不存在时才走捷径」**。睡眠唤醒时会话是「存在但已失效」，如果也走捷径就会误伤一条本来好的连接 —— 所以这种情况必须留给正常循环去探测判定。

**结果**：40 秒 → 约 20 秒。而且这 20 秒里，8 秒是 `rasdial` 跟运营商协商、4 秒是开机本身，**真正能优化的部分已经吃干了**。

## 最后：有些事是解决不了的

写在这里，免得以后自己（或者看到这份文档的人）又去浪费时间：

| 限制 | 原因 | 能不能绕过 |
| --- | --- | --- |
| 睡眠期间无法保持在线 | 只有 Modern Standby，PPPoE 是用户会话内的会话，睡下必然断 | 不能。能优化的只是「醒来多快连回来」 |
| 必须先登录 Windows 才能拨号 | PPPoE 会话由 RasMan 在用户会话维护，SYSTEM 在 session 0 拨不了 | 只能靠自动登录减少摩擦 |
| `rasdial` 的密码会短暂出现在命令行 | 它自身的命令行接口设计如此 | 不能。个人机器可接受，多用户环境要慎重 |
| 探测依赖 ICMP | 脚本目前只实现 ping | 换 TCP 探测可以，但要多写一层 |
| 网卡只跑到 100 Mbps（如果墙上网口就是百兆） | 物理链路 | 先换台机器验证，别只改设置 |

**如果哪天想彻底摆脱「睡眠掉线」这件事**，唯一的根治方案是**把拨号搬到路由器上**（路由器做 PPPoE 拨号 + NAT，电脑只当普通客户端）。那样睡多久都不影响网络，代价是要一台能刷 OpenWrt 的路由器，以及学校可能不允许私接路由器。这个方案我在最开始的选型阶段评估过，最后因为硬件成本和环境限制没走。
