## 2. 一次意外掉线（自愈 4 秒）

```
2026-10-25 17:28:11 [WARN] 疑似掉线（第 1 次探测不通），1s 后复检
2026-10-25 17:28:13 [WARN] 确认掉线（连续 2 次探测不通）| PPPoE=False
2026-10-25 17:28:14 [INFO] 开始重拨：宽带连接
2026-10-25 17:28:15 [INFO] rasdial 退出码=0 输出=... 已连接 宽带连接。 命令已完成。
2026-10-25 17:28:20 [INFO] 连接已恢复正常
```

从「第一次探测不通」到「重新连上」：**4 秒**。

其中 2 秒花在「确认真的断了」上（连续两次探测不通才算），2 秒是 `rasdial` 的协商时间。这个数字已经是这套探测策略的下限。

## 3. 一次睡眠唤醒

```
16:56:09 [INFO] 检测到系统即将进入待机
16:59:46 [INFO] 系统已从待机恢复
16:59:55 [WARN] 疑似掉线（第 1 次探测不通），1s 后复检
17:00:14 [WARN] 疑似掉线（第 1 次探测不通），1s 后复检
17:00:15 [INFO] 开始重拨：宽带连接
17:00:18 [INFO] rasdial 退出码=0 输出=... 已连接 宽带连接。 命令已完成。
17:00:35 [INFO] 连接已恢复正常
```

唤醒后约 **49 秒**恢复。这段日志正是优化的起点 —— 拆开看发现：

- 唤醒到第一次探测之间隔了 **9 秒**（醒来后网络栈要重新初始化）
- 中间那次「疑似掉线」到「确认掉线」隔了 **19 秒**，因为当时还在用 `Test-Connection`（单次 8.5 秒）
- `rasdial` 本身只要 **3 秒**

换成 600ms 超时的 .NET `Ping` 之后，同样的流程降到约 20 秒，而这 20 秒里大部分是醒来后网络栈自愈的固定开销。

## 5. 重拨失败时的退避

如果拨号一直失败（账号欠费、运营商故障、网线没插），日志会是这样：

```
17:10:05 [ERROR] rasdial 退出码=691 输出=... 由于域上的用户名和/或密码无效而拒绝访问。
17:10:05 [WARN] 重拨失败，15 秒后重试（第 1 次）
17:10:20 [ERROR] rasdial 退出码=691 ...
17:10:20 [WARN] 重拨失败，30 秒后重试（第 2 次）
17:10:50 [WARN] 重拨失败，60 秒后重试（第 3 次）
17:11:50 [WARN] 重拨失败，120 秒后重试（第 4 次）
17:13:50 [WARN] 重拨失败，240 秒后重试（第 5 次）
17:17:50 [WARN] 重拨失败，300 秒后重试（第 6 次）
```

退避从 15 秒起翻倍，封顶 300 秒。这样即使网络长时间不可用，也不会疯狂重试把 CPU 和运营商侧的认证服务器刷爆。一旦拨通，退避计数清零。
